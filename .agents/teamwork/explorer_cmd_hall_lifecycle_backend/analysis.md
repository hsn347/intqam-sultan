## 2. التحليل الجذري لمسألة الجمود لمدة 300 ثانية (Root Cause of 300s Stall)

### أ. الأدلة البرمجية المباشرة في `tasks/command_hall.py`
في السطور 65-66:
```python
# أقصى مدة لتشغيل حلقة قاعة القيادة بالثواني (5 دقائق)
LOOP_MAX_DURATION_SECONDS = 300
```
وفي الدالة `run()` السطور 971-1041:
```python
start_time = time.time()
...
while (time.time() - start_time) < LOOP_MAX_DURATION_SECONDS:
    ...
    # إرسال الفيلق
    dispatched, blocked_on_march = await self._handle_march_tasks(hall_data)
    total_marches += dispatched
    ...
    elapsed = int(time.time() - start_time)
    has_active_marches = (total_marches > 0)          # ⚠️ خطأ 1: تراكمي دائم!
    has_preparing_tasks = any(self._safe_int(t.get("statue", 0)) == TASK_STATUE_PREPARE for t in tasks) # ⚠️ خطأ 2: دائم!

    # عدم الخروج مبكراً عند 30 ثانية إذا كانت هناك فيالق مرسلة بالخريطة أو مهام قيد الإعداد
    if not pending_tasks and not has_active_marches and not has_preparing_tasks and elapsed >= 30:
        exit_reason = "تم إنجاز كافة المهام المتاحة بالكامل"
        break

    # فاصل زمني بشري عشوائي بين الدورات (4.0s - 7.0s)
    sleep_sec = random.uniform(4.0, 7.0)
    remaining_time = LOOP_MAX_DURATION_SECONDS - (time.time() - start_time)
    if remaining_time <= 0:
        exit_reason = "انتهاء مدة الدورة الزمنية (5 دقائق)"
        break

    await asyncio.sleep(min(sleep_sec, max(0.5, remaining_time)))
```

### ب. سلسلة التعليق (The Deadlock Chain)
1. في التكرار الأول: يتم إرسال فيلق طليعة (Type 2) أو معركة (Type 5).
2. في السطر 940: `dispatched += 1`، وفي السطر 941: `task["statue"] = TASK_STATUE_PREPARE`.
3. في السطر 1008: `total_marches += dispatched` (أصبح `total_marches = 1`).
4. عند فحص شرط الخروج في السطر 1025:
   `has_active_marches = (total_marches > 0)` -> **`True` بشكل مطلق!**
   `has_preparing_tasks = True` -> **`True` بشكل مطلق!**
5. الشرط `not has_active_marches and not has_preparing_tasks` يصبح `False` بشكل دائم وغير قابل للتغيير.
6. في السطر 977: يتم استدعاء `hall_data = await self._ensure_synced_data()`.
   بالنظر إلى `_ensure_synced_data()` في السطور 555-567:
   ```python
   hall_data = self.get_ctrl("commandHall")
   if self._is_synced and hall_data is not None and isinstance(hall_data, dict):
       return hall_data
   ```
   المتغير `self._is_synced` قيمته `True` من أول استعلام؛ لذلك تُعيد الدالة الكائن المخزن محلياً بالذاكرة فوراً دون إرسال أي استعلام للسيرفر!
7. ينام البوت `sleep(4.0 إلى 7.0)`، ثم يستيقظ ويكرر نفس الفحص، ويعيد قراءة نفس البيانات الراكدة، وينام مرة أخرى.
8. يستمر هذا النمط العقيم لمدة 300 ثانية كاملة (5 دقائق) حتى ينكسر شرط الـ `while` الخارجي، ويسجل الخروج: `exit_reason = "انتهاء مدة الدورة الزمنية (5 دقائق)"`.
9. أثناء هذه الدقائق الخمس، تكون حلقة القلعة بالكامل في `bot_manager.py` (السطر 643: `await task_instance.safe_execute()`) معلقة وتنتظر انتهاء قاعة القيادة.

## 3. التحليل الجذري لمشكلة عدم استلام المكافآت (The 0-Rewards Claiming Issue)

### مقارنة سلوك أنواع المهام في الكود الحالي:

| نوع المهمة (Task Type) | آلية التنفيذ | آلية التحديث | استلام الجائزة | النتيجة الحالية |
|---|---|---|---|---|
| **النوع 1: فيلق الغزاة (Rebel Group)** | هجوم استباقي `CMD 2274 / SubCMD 7` (0 طاقة) | مباشر في الذاكرة عبر استجابة السيرفر الفورية | `CMD 2274 / SubCMD 8` (commitType=1) | تُستلم بنجاح إذا كانت الطاقة كافية أو هُزم الفيلق |
| **الأنواع 3، 4، 6: المهام الفورية (Dialogue, Rescue, Snipe)** | إنجاز فوري `CMD 2274 / SubCMD 5` | يتم ضبط `statue = FINISH` محلياً (السطر 813) | `_claim_finished_tasks()` يُستدعى فوراً بعدها (السطر 1003) | تُستلم بنجاح (وهذا ما أثبته فحص beetoo1 للمهام 3091 و 6091) |
| **النوعان 2 و 5: مهام الفيالق (Pioneer, Battle)** | إرسال مسير على الخريطة `CMD 1007 / SubCMD 2` | تُضبط الحالة محلياً إلى `PREPARE` (السطر 941) ولا يتم الاستعلام بعدها أبداً | تفحص `statue == FINISH` ولا تجد أي مهمة بهذا الرقم | **فشل الاستلام والخروج بـ 0 مكافأة!** |

### سبب عدم الاستلام لمهام الفيالق:
1. استجابة أمر إرسال الفيلق `CMD 1007 / SubCMD 2` (`ADD_KINGDOM_QUEUE`) لا تحتوي على كائن `initData` لقاعة القيادة، بل تحتوي على بيانات الطابور الخارجي (`queueId` / `retdata`).
2. يتم تحويل حالة المهمة في الذاكرة إلى `statue = TASK_STATUE_PREPARE` (1).
3. الفيلق يتحرك على الخريطة، ويصل لهدف الغزاة، ويحسم المعركة في سيرفر اللعبة خلال 10 إلى 25 ثانية.
4. في سيرفر اللعبة، تصبح حالة المهمة رسمياً `statue = 3` (`TASK_STATUE_FINISH`) وتُضاف إلى `finishTaskData`.
5. لكن كود `CommandHallTask` يمتنع عن إرسال `CMD 2274 / SubCMD 1` لمزامنة الحالة الحقيقية.
6. دالة `_claim_finished_tasks()` تبحث عن المهام ذات `statue == 3`. ونظراً لأن المهمة في ذاكرة البوت لا تزال برقم `1`، يتخطاها الاستلام تماماً.
7. بعد 5 دقائق من النوم العقيم، تنتهي الدورة وتُغلق المهمة بإجمالي جوائز = 0!

## 4. معمارية تتبع الفيالق في البوت وفي كود اللعبة (March Tracking Architecture)

### أ. فحص مهام البوت الأخرى (`tasks/gather.py`, `tasks/monster.py`, إلخ):
- من خلال المسح الشامل لمجلد `tasks/`، تبين أن مهام الجمع والوحوش والحشود (`gather`, `monster`, `rally`) **غير موجودة بعد في المشروع**.
- مهمة قاعة القيادة (`CommandHallTask`) هي **المهمة الأولى والوحيدة الرائدة في المشروع التي ترسل مسيرات جيوش على الخريطة (`CMD 1007 / SubCMD 2`)**.

### ب. كيفية استقبال وتتبع طوابير الفيالق عبر البوابة (`core/game_client.py`):
1. **في الذاكرة الحية الحالية**:
   - السطر 1438 في `core/game_client.py`:
     ```python
     if notify_id == 'NOTIFY_LOCAL_QUEUE_SYNC' and isinstance(notify_data, list):
         self.local_queues = notify_data
         self.init_data['queueCtrl'] = {"queues": notify_data}
     ```
   - كل طابور مسير في `notify_data` هو كائن يطابق `kingdomQueueObjCell.lua` ويحتوي على:
     - `id`: معرف طابور المسير.
     - `moveLineType`: نوع خط المسير (15 لفيالق قاعة القيادة: `MOVE_LINE_TYPE_COMMAND_HALL_NPC`).
     - `status`: حالة المسير (متحرك، يقاتل، عائد).
     - `statusStartTime`: توقيت بدء المسير بالثواني.
     - `statusEndTime`: توقيت الوصول أو الانتهاء بالثواني.
     - `to`: إحداثيات الهدف `{"x": target_x, "y": target_y}`.
     - `taskData`: بيانات المهمة المرفقة `{"index": task_index, "type": task_type}`.
2. **غياب معالج إشعارات قاعة القيادة**:
   - السيرفر يرسل إشعار الدفع `NOTIFY_COMMAND_HALL` (الأمر `1009`، المعرف الفرعي `608`) عند حسم معارك قاعة القيادة (`PIONEER_TASK = 4`, `COMMON_TASK = 5`).
   - `core/game_client.py` لا يحتوي على معالج لـ `1009/608` حالياً، مما يجعل الاعتماد الحصري على إشعارات الذاكرة التلقائية غير كافٍ لقاعة القيادة ما لم يتم تفعيل مزامنة شبكية دورية أو تتبع زمني ديناميكي.

### ج. حساب زمن المسير ديناميكياً (Dynamic March ETA):
1. **قرب أهداف قاعة القيادة**:
   - أهداف مهام قاعة القيادة (طليعة 2، معركة 5) تظهر دائماً على الخريطة بالقرب من قلعة اللاعب، في نطاق دائري يتراوح بين **1 إلى 5 مربعات (Tiles)** فقط من إحداثيات القلعة الحالية (`cityCtrl.cinfo.pos`).
2. **المعادلة الرياضية لزمن الوصول**:
   $$\text{Distance} = \sqrt{(target_x - castle_x)^2 + (target_y - castle_y)^2}$$
   - سرعة الفيلق إلى أهداف قاعة القيادة تتراوح بين 2.0 إلى 3.5 ثانية لكل مربع.
   - زمن الذهاب: بين **5 إلى 15 ثانية**.
   - زمن حسم المعركة: **1 إلى 2 ثانية**.
   - زمن الإياب: بين **5 إلى 15 ثانية**.
   - **الزمن الكلي لدورة الفيلق كاملة: 15 إلى 35 ثانية فقط!** (وليس 300 ثانية).

## 5. خطة التنفيذ الموصى بها لإصلاح دورة الحياة بالكامل (Actionable Implementation Plan)

### الخطوة 1: القضاء على جمود الـ 300 ثانية (Eliminating the 300s Freeze)
- إلغاء الثابت الكارثي `LOOP_MAX_DURATION_SECONDS = 300` واستبداله بمهلة أمان قصوى لحلقة المهمة قدرها **60 ثانية** فقط (Watchdog Timeout).
- تصحيح تعريف الفيالق النشطة:
  - استبدال `has_active_marches = (total_marches > 0)` بـ تتبع حقيقي لقائمة الفيالق قيد المسير: `active_in_flight_marches: Dict[int, float]`.
  - عند إرسال فيلق للمهمة ذات الفهرس `task_index`، يتم تسجيله:
    `active_in_flight_marches[task_index] = time.time() + eta_seconds`.
  - بمجرد اكتمال الفيلق واستلام جائزته، يُحذف من القاموس.
- الخروج الفوري النظيف: إذا لم تكن هناك أي مهام بحاجة لتنفيذ (`statue in (BEGIN, FINISH)`) ولا توجد فيالق نشطة قيد المسير (`len(active_in_flight_marches) == 0`)، تخرج المهمة فوراً دون أي انتظار إضافي (يستغرق التنفيذ حينها 3-5 ثوانٍ فقط للمهام الفورية).

### الخطوة 2: التتبع الديناميكي لخطوط المسير (Dynamic March Tracking)
- بعد إرسال الفيلق عبر `CMD 1007 / SubCMD 2`:
  - استخراج إحداثيات القلعة من `conn.init_data['cityCtrl']['cinfo']['pos']` وإحداثيات الهدف `(target_x, target_y)`.
  - حساب المسافة وزمن الوصول المقدر: `eta = max(8.0, min(30.0, distance * 3.0 + 3.0))`.
  - فحص `conn.init_data.get('queueCtrl', {}).get('queues', [])` للتحقق مما إذا كان هناك طابور مسير بنوع `moveLineType == 15` وقراءة `statusEndTime` إن وجد.
  - الانتظار الذكي (Smart Non-blocking Wait): الانتظار حتى حلول موعد الوصول المقدر `eta` عبر فواصل نبضية خفيفة (2.0s - 4.0s) تسمح لمعالج الأحداث بالعمل دون تجميد.

### الخطوة 3: المزامنة الآمنة عبر `CMD 2274 / SubCMD 1` فور وصول الفيلق
- إنشاء دالة صريحة `_refresh_hall_data(force=True)`:
  - تقوم بإرسال استعلام المزامنة `CMD 2274 / SubCMD 1` (`REQ_COMMAND_HALL_INIT`).
  - تحديث كائن الذاكرة الحية `conn.init_data["commandHall"]` ومحتويات `hall_data`.
- استدعاء المزامنة:
  1. فور وصول الفيلق لموقعه وتجاوز الـ ETA.
  2. بعد استلام مكافأة هزيمة جيش الغزاة الجماعي (Type 1) لضمان سحب الدفعة والموجة التالية من المهام.

### الخطوة 4: الاستلام الفوري لكافة الجوائز المستحقة (`CMD 2274 / SubCMD 8`)
- بمجرد نجاح المزامنة بعد وصول الفيلق:
  - يظهر الفيلق في `hall_data` بحالة `statue == TASK_STATUE_FINISH` (3) أو في `finishTaskData`.
  - تقوم `_claim_finished_tasks()` فوراً بإرسال أمر الاستلام الرسمي `CMD 2274 / SubCMD 8` (`REQ_COMMAND_HALL_COMMIT_TASK`) بـ `commitType` والفهرس المناسب.
  - إضافة نقاط الخبرة والمكافآت، وفحص الترقية التلقائية للمستوى (`CMD 2274 / SubCMD 2`).
  - تسجيل الجوائز المستلمة ورفع عداد `total_claimed > 0`.

### الخطوة 5: تجديد المهام والانتقال الفوري للدفعات التالية (Task Renewal & Wave Transition)
- عند هزيمة فيلق الغزاة الجماعي (Type 1):
  - استلام مكافأته عبر `CMD 2274 / SubCMD 8` بـ `commitType = 1`.
  - هذا الاستلام يرفع تلقائياً `armyGroupID` إلى المستوى التالي، مما يولد فوراً في السيرفر دفعة جديدة من المهام (مهام حوار، إنقاذ، قنص، معارك).
  - بعد استلام Type 1، يتم استدعاء `_refresh_hall_data(force=True)` مباشرة لقراءة الموجة الجديدة من المهام وتنفيذ المهام الفورية منها واستلامها في نفس الدورة دون توقف!
